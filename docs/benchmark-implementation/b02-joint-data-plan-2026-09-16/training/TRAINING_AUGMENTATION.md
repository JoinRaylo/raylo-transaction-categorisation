# Training-input audit and augmentation plan — 2026-09-16

This is an aggregate-only audit of the current research inputs. The protected v5
and v6 files were not opened. Counts below come from
[`aggregate_profile.json`](aggregate_profile.json), generated by
[`profile_training_inputs.py`](profile_training_inputs.py). The profile records
before/after SHA-256 fingerprints for each row source it reads; the profile script
itself is also hashed in the output.

## Current files and recipes

The current hinge training file is
`outputs/tuning_train.jsonl` (414,400 rows, SHA-256
`fd26cde73e7aa3483771adc90b413f2c0c9f4274f9c6b532bb7698e708fe0742`). Its
companion validation file is `outputs/tuning_val.jsonl` (5,000 rows, SHA-256
`47b6d22534ca498ad31ab600786b91932cfac138d0f26bc70aba3a77cf29c13c`). The
current consensus source is `data/distillation_labels_consensus.parquet`
(404,982 rows, SHA-256
`fa8e7680e2f04178874e977a8901e08e3e9e4283bd51de46f0e10c0cd6256fb3`).

The hinge recipe in `src/retrain_corrected_heads.py` fits a fresh character
TF-IDF vectorizer (char-wb n-grams 2–5, 30,000 features, `min_df=2`), adds
`log1p(abs(amount))` and direction, then fits an SGD hinge classifier
(`alpha=1e-6`, 50 iterations, fixed seed). It consumes all 414,400 rows.

The saved iteration-8 transformer recipe is the DistilBERT domain-adapted
encoder followed by two supervised stages. The consensus stage is represented
by `outputs/distill_models/txn_classifier_distilled/train_meta.json`: 404,264
rows after direction legality filtering, two epochs, cap 25,000 and floor 200.
The gold stage is represented by
`outputs/distill_models/txn_classifier_gold_distilled_s{42,7,123}/train_meta.json`:
414,196 rows after the same legality filtering, uncapped (`1e9` cap), floor 300,
four epochs, with seeds 42, 7 and 123. The selected epoch is recorded in each
metadata file. The transformer therefore starts from the same tuning source as
the hinge, but its effective pool differs: 204 rows are removed by its direction
mask and its per-epoch floor repeats thin leaves. The two heads share source
lineage, not identical row weighting or effective exposure.

The older `silver_labels.parquet` is retained as an artifact (1,895,276 rows,
SHA-256 `f1a6068891864aed1c247c093709539e805d5370d7dae8541c6497453243350b`),
but it is not the current iteration-8 supervised source. The profile also records
the legacy `distill_train.parquet` metadata without treating it as a current
recipe.

## Aggregate profile

`tuning_train.jsonl` has 384,114 debit rows (92.7%) and 30,286 credit rows
(7.3%). Merchant text is blank on 32,783 rows (7.9%). The exact user-message
projection contains 342,268 unique logical inputs and 342,405 unique
input-plus-label pairs. There are 133 logical inputs with conflicting labels and
71,995 rows beyond the unique input-plus-label count; these are repeated or
oversampled exposures, not additional independent examples.

The largest supports are concentrated in `transfer_p2p` (118,195 rows),
`convenience_store` (30,331), `restaurant_cafe` (26,039), `pub_bar` (18,178),
`unclassified_other` (15,472), `takeaway` (15,421), `groceries` (14,413) and
`fuel` (11,518). Exact unique input counts by label are available in the JSON
profile; selected examples are `transfer_p2p` 100,945, `debt_collection` 817,
`gambling_casino` 419, `cash_advance` 74, `charge_card_repayment` 77,
`overdraft_unarranged` 77, `balance_transfer` 29 and
`financial_services_other` 99.

The current taxonomy has 275 leaves. Four leaves have no tuning-train row:
`account_misuse`, `balance_transfer_fee`, `interest_charged` and
`loan_repayment_dd`. No out-of-taxonomy labels were observed. These absences are
coverage gaps to review, not instructions to synthesize labels.

Credit coverage is both sparse and concentrated: 203 labels occur at least once,
but 100 credit-direction labels have fewer than five rows, 134 have fewer than
10, and 160 have fewer than 20. Credit rows are led by `transfer_p2p` (14,726),
`transfer_bank_unspecified` (2,614), `savings_transfer` (1,949), `salary`
(1,708), `refund_received` (1,630), `benefits_state` (1,245),
`income_other_unspecified` (1,007) and `loan_disbursement` (602). Debit support
is much broader: only three debit-direction labels have fewer than five rows.
This supports credit-side, direction-compatible augmentation rather than global
oversampling of already large transfer classes.

The current consensus pool has 404,982 rows: 87,610 credits and 317,372 debits;
119,262 rows have blank merchant text. All rows are Plaid and carry the
`agent_consensus` tier. This is a useful weakly supervised transformer stage,
but it is not independent ground truth.

## Augmentation priorities

1. Create customer/account/event-disjoint reserves and an independent evaluation
   set before selecting any new training rows. Keep selection validation separate
   from the sealed confirmation role. Apply view-specific input and family
   protection, retaining source lineage and exposure status per row.
2. Target the measured credit-direction gaps, especially labels with fewer than
   20 credit rows where valid source labels and the declared direction policy support
   that category. Do not infer a label from merchant text alone or mechanically fill
   every leaf/direction cell. Capture any proposed direction-mask change for review. Keep the large transfer classes from absorbing
   the candidate budget.
3. Add carefully reviewed examples for the thinnest debit leaves only where the
   taxonomy permits debit. Keep the existing risk top-up as historical evidence;
   do not treat its provider crosswalk or tiebreak labels as independent truth.
4. Treat blank-merchant examples as a first-class input view. They are 7.9% of
   the tuning file and nearly all of the credit/risk top-ups. Preserve raw
   narrative-derived examples only inside approved private candidate artifacts;
   no merchant or narrative field belongs in aggregate reports.
5. Build one frozen candidate snapshot for both heads. The hinge should fit its
   vectorizer only after that snapshot is frozen. The transformer should retain
   its current domain-adapted encoder/tokenizer for the supervised retrain unless
   a separately approved MLM experiment is chosen. Train both heads in parallel,
   with their actual filtering, masks and repeat policies recorded independently.

The existing v8 and iteration-8 reports remain development evidence. This audit
adds no new model scores or evidence of accuracy improvement.

## Safe sequence

Reserve customer/account/event-disjoint evaluation and confirmation views first;
then freeze view-specific input/family protection and provenance checks. Build
candidate pools from eligible historical material when permitted, excluding
protected assets and any row with unknown provenance from forced training. Keep
selection validation separate. Train hinge and transformer candidates in parallel
from the same frozen candidate snapshot while preserving their head-specific
feature projections. Declare the candidate recipe and augmentation policy before
fitting, use the separate selection set for epoch/checkpoint choice, freeze the
actual selected fitted artifacts and metadata, and then run sealed confirmation. Existing
v5/v6 rules remain unchanged.

The JSONL uniqueness numbers above are exact user-message projections. CSV
uniqueness uses the available merchant/description/amount/direction tuple; parquet
uniqueness uses its stored raw text when present. These are source-input measures,
not account/event identity and not the hinge sparse or transformer token
projections. No new performance claim is made here.

Recipe/source and relevant saved metadata hashes are pinned in [recipe_evidence.json](recipe_evidence.json). These retained files corroborate the documented recipe; they are not original fit-consumption receipts. Parent reaggregation of both JSONL files is retained in [independent_training_check.json](independent_training_check.json).
